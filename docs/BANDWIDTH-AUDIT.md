# Bandwidth and sample-rate audit (3.6)

Owner demand: every mode lets the user set ANY bandwidth and ANY sample rate; the default stays the default; a limit may only warn; if the radio or its driver cannot do it the app says so plainly with the real limit. This file is generated by `tools/gen_bandwidth_audit.py` from the code (`build/test_custom_bandwidth_all --csv --rows`) and checked by `ctest -R custom_bandwidth_all`.

## The one mechanism

- **Plan (shared by every mode)**: `app/state/rx_width.h` `rxApplyWidth()` / `rxApplyRate()`. `applyBandwidth()` (the app), `ServerHost::buildTune()` (the headless server, web client, MCP) and the all-modes test make the same call. Off (the default): the mode's own bandwidth, rate and radio filter are untouched. On: the radio's sample rate is the width / 0.9 rounded up to 0.25 Msps (never below the decoder's own floor), the radio's analogue filter is 0.9 of that rate, `TuneSettings::bandwidthMhz` is the width. The sample rate can also be typed on its own (`rate.<mode>.<radio>`); a typed rate wins.
- **Persisted** per mode and per protocol entry (`rxbw.<id>`, `rxbw.<id>.custom`; the id is the protocol entry's own, e.g. `ft8`, `pocsag`, `meshtastic`, else the mode's).
- **UI**: the Advanced row of every mode (top bar, side panel, setup row): `Bandwidth: <standard> (standard)  [ ] Custom` + `Sample rate: ... [ ] Custom` + **Reset to default** (shown while either is custom). **Simple view**: a compact chip `Bandwidth: default 1.8 MHz` / `custom 5 MHz` in the Command view; click it for the same entry (a number in MHz, `250k` for kHz, any positive value, no slider), a `!` warning and Reset to default. Warnings only: below the decoder's need, outside what the radio lists, in a gap of its ranges. A radio's refusal shows the driver's own message and puts the previous setting back.
- **Remote**: `POST /api/v1/capture_bandwidth` (`hz`, `khz` or `mhz`; 0 = the mode's own), MCP `set_radio` `capture_bandwidth_khz`, headless server (`capture_bw_mhz` in its state file). `/api/v1/samplerate` and `/api/v1/bandwidth` lost their 1 GHz sanity caps (finite, positive is the only test).
- **Whole-span decoding**: the HF digital / CW / PSK span cap (250 kHz, 100 kHz for PSK, 64 kHz for RTTY) is now a default, lifted when a custom bandwidth is set (`setWideSpanCapHz`); the voice banks (DMR, P25, NXDN, dPMR, M17, D-STAR, pagers, packet, MPT1327, Fusion, LTR, EDACS) and TETRA already decode every carrier in a wider capture.

## Counts

- Engine standards with a tuning (plus the six classic families and a plugin mode in the test): **151**. Mode-table rows: **182** (of which 2 have no tuning: IPTV, the Mode Builder and Plugins managers, which have no radio capture; their plugin / builder modes register one).
- Had a custom-bandwidth control before 3.6: all of them in the Advanced row (3.4), none in the Simple view, none with a Reset or a width warning.
- Applied correctly by the receiver before 3.6: all but DVB-T2 / DVB-T / DTMB (3 receivers, 2 families). After: all.
- Hard clamps on the bandwidth / rate / span path before: 5 (whole-span cap, 3 receivers + decimator; two remote caps) + the 3.4 list in `docs/LIMITS-AUDIT.md`. After: 0 on the capture path; the remaining fixed lists are protocol or audio parameters (below).

## Still not covered, and why

- **Decode at a wide capture (4x) was measured for the 11 modes that finished (dab, fm, dvbs2, dmr, adsb, sonde, ais, acars, iridium, hfdl300 and the run for navtex stopped)** (`sens_sweep --wide 4`), not for the other ~140: they have a test signal and start at the planned rate, but no clean-signal valid-unit harness. They run at the rate and process signal; whether every one decodes as well as at its own rate needs a signal per mode.
- **Wide captures against the CPU**: the HF whole-span decoders run one decoder per ~3.4 kHz slice, so a 1 MHz span is ~290 decoders. The cap is gone; the processor is the limit and the CPU guard of the bank applies where there is one.
- **A real HackRF at 20 Msps and above**: nothing here was run on a radio (no radio on the test machine). The plan is exact; the driver has the last word, and its refusal is shown.
- **Modes whose decoder cannot use a wider rate**: none found in the engine standards; a decoder whose floor is above the custom rate warns (and logs "cannot work") instead of being blocked.
